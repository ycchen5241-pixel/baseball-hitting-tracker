## 一、目標與商業模式

- **對象**：目前一人開發，但目標是未來公開讓其他人使用／販售，不是純自用工具。
- **商業模式**：Freemium 訂閱制。MVP 階段不收費。
- **授權後果**：因為有公開/商用意圖，模型授權問題（見四、2）現在就必須解決，不能延後。

## 二、為什麼要做成「App」

驅動力原為**球場現場需要離線使用**——不想依賴筆電或網路連線，這個前提排除了「錄完上傳伺服器分析」的選項。

**2026-08-11 決策調整**：現階段不再要求離線，改採**中心化伺服器**架構——分析邏輯維持現有 Python 實作原封不動跑在伺服器上，手機 App 只負責錄影、上傳、顯示結果，透過網路呼叫伺服器 API。「不在乎離線」是現階段判斷，還是長期定案，尚待之後回頭確認（見八）。

## 三、使用情境

**錄完事後分析**，不是錄影當下即時疊圖。這個決定讓「分析放哪裡跑」的選項不必考慮即時串流演算法的重寫成本；**2026-08-11 起**「分析放哪裡跑」進一步確定為伺服器端（見二、四之1），手機只需上傳錄好的影片、等待伺服器回傳結果。

## 四、技術架構

### 1. 演算法搬遷策略

**2026-08-11 決策更新**：原生重寫（Swift/Kotlin）方案推翻，改採 **Python 中心化伺服器 + Android 前端呼叫**：現有 Python 管線（YOLO 偵測 → `CloudBallTracker`/`BatCloudTracker` 密度聚類 + Sequential RANSAC 軌跡擬合 → `physics/pipeline.py` 物理計算）原封不動跑在伺服器上，Android App（`AndroidStudioProjects/baseball_tracker`，已有 Jetpack Compose UI 骨架：Home / Recording / Calibration / FpsConfirm / Results / History / Me 等畫面）只負責錄影、上傳影片、呼叫伺服器 API、顯示結果，不需要把演算法移植成另一種語言。

決策考量：
- 原本否決「嵌入 Python runtime（Chaquopy）」是因為要在**手機上**執行 Python，體積與速度是顧慮；中心化伺服器方案不受這個限制，同時完全消除了原生重寫「跟 Python 版本分岔不同步」的核心風險——`待決問題.md` 記錄的頻繁 EV 公式修訂（如 2026-07-26 從「除以 cos(仰角)」改為「vx/vy 各自迴歸再合成」），現在只需改一份 Python 程式碼，不會有第二份實作要同步。
- 前提交換：原本「球場現場離線使用」的驅動力被移除，App 需要網路連線才能取得分析結果（見二）。
- **授權風險不因此消失、反而更直接命中**：AGPL-3.0 的 Affero 條款正是針對「使用者透過網路與程式互動」的情境設計，伺服器化部署比手機端閉源推論更直接落入此條款適用範圍。下方 4-2 的 NanoDet-Plus 重訓練決策，優先順序因此從「手機部署最佳化考量」提高為**授權合規的必要條件**。

### 2. 模型與授權

- **問題**：現有 `best_v7.pt` 是用 `ultralytics`（AGPL-3.0）套件訓練，Ultralytics 官方立場是用其程式碼訓練出的模型權重也受 AGPL-3.0 拘束。若要商用又不開源，換手機端推論框架並不足夠，必須連訓練流程都換成非 Ultralytics 的架構重新訓練。
- **決定**：改用 **NanoDet-Plus**（Apache 2.0）。
  - 現有 Roboflow 標注資料集（ball / bat / bat_head / bat_tail / home_plate，累積至 v7 版的全部標注）可直接以 COCO JSON 格式匯出沿用，不需重新標注。
  - Colab 訓練環境可沿用，僅訓練腳本/設定檔（NanoDet 用 YAML 設定 `num_classes` 等）需重寫。
  - ~~手機部署：NanoDet-Plus 官方提供 TFLite/NCNN 匯出腳本~~（**2026-08-11 起不適用**：伺服器端架構下模型直接以 PyTorch/ONNX 在伺服器推論，不需要手機端 TFLite/NCNN 匯出這一步；相容性優於 YOLOX 這點對伺服器部署不構成決策因素，但重訓練本身仍為授權合規必要條件，決定不變）。
  - **已知風險**：NanoDet-Plus 為追求輕量犧牲部分精度，對小型快速移動物體（球）的偵測能力可能不如現有 YOLO 調校 7 版的效果，需在驗收階段特別檢查。
  - **驗收門檻**：重訓後球的偵測率須達到與現有 `best_v7.pt` 同等級，未達標前不得取代。
- **副作用（已解決）**：换成 Apache 2.0 授權後，之前顧慮的「AGPL Affero 條款會拖累未來雲端付費服務也要公開原始碼」的問題不再適用——App 可以是 closed source。

### 3. 平台順序

**Android 優先**做出 MVP，iOS 之後再做（一人開發，不同時做兩個原生平台）。

## 五、MVP 範圍

**僅支援 T座（tee）打擊情境**。理由：T座場景的球體軌跡判斷與球速已用測速槍實測驗證過、可信賴；投球（pitch）場景目前只有「场景本身偵測得到」，EV/仰角數值尚未做過同等驗證。

架構備註：T座與投球共用同一套重量級運算（`TrajectoryFitter` RANSAC 曲線擬合、密度聚類、MAD 濾波），EV/仰角計算本身也不分場景。因此投球模式加入時**程式碼複雜度低**（主要是 `_detect_scenario()` 場景判斷邏輯 + 投球版本的接觸幀判定），真正的前置條件是**先完成投球場景的 ground truth 驗證**，而非架構工作量。

側拋（sidetoss）場景本輪討論未涉及，暫不在 MVP 規劃內。

## 六、現場操作設計

### 1. 機位校準

- App 顯示提示字卡（範例參考 B4 App 的三腳架擺放距離圖卡：如「離本壘板前緣 80cm、寬度 180cm」等固定尺寸建議），提醒使用者如何架設手機與三腳架。
- **卡片僅為輔助提醒，不強制、不作為固定校準常數**——實際 EV/仰角計算仍以現有 `validate_homography()` 事後實測推算（本壘板 bbox 反投影）為準，因為使用者現場擺位不會精準符合卡片建議的數字。此設計與現有程式碼架構完全相容，不需改動 homography 驗證邏輯。

### 2. 240fps 設定確認

- 專案設計基準為 240fps（`constants.VIDEO_FPS`）。
- 錄影前顯示字卡提醒使用者需將手機慢動作模式調整為 240fps，字卡為通用提醒，不做各廠牌（Samsung/Pixel/小米等）選單路徑的客製化教學。
- **錄影後自動偵測實際 fps**（沿用 `待決問題.md` F2 已有的 fps/掉幀偵測邏輯）：若偵測到明顯非 240fps，跳出警告告知「可能影響精準度」，但**不擋下分析、仍繼續執行**，是否信任本次結果由使用者自行判斷。**2026-08-11 起**：此邏輯維持原 Python 實作跑在伺服器端，不需要移植到 Kotlin。

## 七、團隊與資源現況

目前僅一人開發，無其他行動開發或 ML 部署人力協作。這是「Android 優先、Python 伺服器 + 前端呼叫、NanoDet-Plus 選型」等範圍收斂決策的前提條件，資源改變時應重新評估平台/範圍計畫。**2026-08-11 決策調整後**，一人開發的負擔從「同時維護兩份演算法實作（Python + Swift/Kotlin）」降為「一份 Python 演算法 + 一個輕量前端」，直接對應資源限制。
