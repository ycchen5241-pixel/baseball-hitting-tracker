# BatCloudTracker 片段合併機制（圓弧倒推驗證）— 已知狀態與待驗證問題

適用範圍：`detector/bat_tracker_cloud.py` 的 `_find_all_curve_runs` /
`_try_merge_fragments` / `_find_swing_in_segment`。

## 這個機制在解決什麼問題

轉向角掃描（`_turn_angles` + `_find_all_curve_runs`）用「單步轉向幅度
夠大 + 方向持續同一個正負號」判斷連貫路徑，這個判斷對單一取樣點是
零容忍的——只要一個點因為缺偵測、位移太小、或路徑本身曲率天生較低
而不合格，就會把本來屬於同一次揮棒的連續路徑切成好幾個獨立片段。

`_try_merge_fragments` 想解決的問題：對時間相鄰的片段，用 RANSAC 圓弧
擬合倒推驗證——如果兩個片段的點各自都有夠高的內點率落在同一個擬合圓
上，判定它們其實是同一段揮棒被誤切，接受合併。

完整的討論脈絡（為什麼放棄直接對整個區段做圓弧擬合、為什麼改用轉向角
掃描、為什麼轉向角掃描又需要片段合併補救）請見對話紀錄，這裡只記錄
實作現況跟已知問題。

## 實測狀態（IMG_3294，2026-07-12 前後測試）

**這個機制確實有被觸發過，不是完全沒作用**，但實測結果比預期複雜：

用 `_find_all_curve_runs` 對真實資料的主要區段（frame 211-1038）掃描，
找到 13 個片段，其中幾個比較大的：

```
frame 839-897  (45 pts)  ← 目前輸出視窗 (839,882) 的來源
frame 916-917  (2 pts)   ← 太小，低於 BAT_CLOUD_MERGE_MIN_FRAGMENT_POINTS(3)
frame 919-970  (28 pts)
frame 975-992  (18 pts)
```

直接測試合併結果：

- `839-897` × `919-970`：**合併驗證沒有通過**（不在同一個擬合圓上）
- `919-970` × `975-992`：**合併驗證通過**，成功合併成 `919-992`
- `839-897` × `916-917`：因為 `916-917` 點數不足，被點數門檻擋掉，沒有進入圓弧驗證

但最終 `swing_windows` 輸出仍是 `[(839, 882)]`——因為 `_find_swing_in_segment`
在同一個區段內，多個候選（包含合併後的 `919-992`）都通過門檻時，是取
**峰值速度最高**的那一個當最終結果，而 `839-882` 這段的峰值速度比
`919-992` 高，所以合併成功的 `919-992` 雖然存在、也通過了驗證，但沒有
被選為最終輸出。

## 已知問題 1：小片段會卡住合併鏈，讓本該比對的兩段永遠沒機會比對

`_find_swing_in_segment` 目前用「依序掃過片段列表，跟前一個（可能已
合併過的）結果比對」的貪婪演算法：

```python
merged = [runs[0]]
for frag in runs[1:]:
    result = _try_merge_fragments(seg, merged[-1], frag, frame_width)
    if result is not None:
        merged[-1] = result
    else:
        merged.append(frag)
```

問題：`839-897` 要跟 `919-970` 比對合不合，中間隔著一個只有 2 點、
連參與驗證資格都沒有的 `916-917`。演算法會先拿 `839-897` 去跟
`916-917` 比對（因為點數不足被拒絕），然後 `916-917` 自己變成
`merged` 列表裡獨立的一項，接下來換 `916-917` 去跟 `919-970` 比對
（一樣因為 `916-917` 點數不足被拒絕）——**`839-897` 從頭到尾沒有機會
直接跟 `919-970` 比對**，因為演算法只會跟「緊接在後面那一個」比，不會
跳過不合格的小片段去找下一個夠格的候選。

這次直接測試證實 `839-897` 跟 `919-970` 就算真的比對了也不會通過
（不在同一圓上），所以這次沒有造成實際影響，但**這是一個真實存在、
還沒修的邏輯漏洞**：如果哪次資料剛好是「兩個真正該合併的大片段中間
夾了一個小片段」，目前的演算法會因為貪婪掃描的順序問題而永遠不會去
嘗試那次合併。之後如果要修，方向是「跳過點數不足的片段，往後找下一個
夠格的候選再比對」，而不是照片段順序機械式地一個一個比。

## 已知問題 2：`839-897` 為什麼跟 `919-970` 合不起來，還不確定原因

有兩種可能，目前無法分辨：

1. **這兩段真的是不同的物理弧線**——如果揮棒路徑是「倒鉤」（兩段不同
   半徑的弧線接起來），839-897 可能是下棒段、919-970 可能是延伸段，
   兩者半徑本來就不同，用同一個圓去驗證，本來就該驗證不過。這種情況
   下「合不起來」是正確行為，不代表機制有問題，代表現有的「單一圓」
   驗證模型天生沒辦法處理複合曲率的倒鉤形狀，需要更進階的模型（例如
   橢圓擬合、或兩段圓弧分開擬合）才能確認它們屬於同一次揮棒。

2. **RANSAC 在這個尺度下還是不夠穩定**——雖然片段本身已經先被轉向角
   掃描驗證過是連貫的，理論上比之前對整個區段直接擬合穩定，但沒有
   實際驗證過這次「合不起來」是不是單純運氣不好（例如 RANSAC 迭代
   次數不夠、剛好抽樣沒抽到好的三點組合）。

**這點需要之後拿更多樣本測試才能確定，不是這次可以下定論的。**

## 已知問題 3：所有合併相關的門檻數值都未經校準

`BAT_CLOUD_MERGE_MAX_GAP_FRAMES`（15，基準30fps）、
`BAT_CLOUD_MERGE_MIN_FRAGMENT_POINTS`（3）、
`BAT_CLOUD_MERGE_MIN_INLIER_RATIO`（0.6）、
`BAT_CLOUD_ARC_RANSAC_ITERATIONS`（200）、
`BAT_CLOUD_ARC_TOL_FRAME_WIDTH_RATIO`（0.015）

這些全部是設計時的起始猜測值，只在這一支影片的一次測試中跑過，**沒有
拿不同影片、不同揮棒風格、不同攝影機距離的樣本驗證過**。尤其
`BAT_CLOUD_MERGE_MIN_INLIER_RATIO=0.6` 這個門檻是否合理、`939-970` 跟
`975-992` 能合併是不是「剛好卡在門檻邊緣的僥倖」還是「真的很穩固的
判斷」，都還不知道。

## 之後遇到問題時的排查提醒

**這個機制不是最終版，之後如果揮棒視窗判斷出現問題，不能預設一定是
這個機制的鍋，也不能預設一定不是**——需要實際debug才知道，可能是：

- 上游的轉向角掃描本身切錯段落（跟這個機制無關，是更早的階段）
- 靜止叢集排除、Bat bbox 補洞等更早的階段出錯
- 這個合併機制本身的門檻不適用於新的測試資料
- 已知問題 1（小片段卡住合併鏈）在新資料上真的造成影響
- 已知問題 2（單一圓模型沒辦法處理複合曲率）在新資料上真的造成影響
- 單純是「這次的揮棒沒有被切段，合併機制根本沒被觸發，問題出在別的地方」

排查時建議直接用 `_find_all_curve_runs` 印出所有片段、用
`_try_merge_fragments` 個別測試候選組合，比單純看最終 `swing_windows`
輸出更容易定位問題出在哪一層。
